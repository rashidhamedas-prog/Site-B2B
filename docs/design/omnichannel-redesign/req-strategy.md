# سند نیازمندی راهبردی — بازطراحی «کانال انتشار» (Omnichannel)
**نگارنده:** دیدگاه مدیرعامل هلدینگ (حامد رشید) | **تاریخ:** ۵ آبان ۱۴۰۵ (۲۷ اکتبر ۲۰۲۶) | **وضعیت:** پیش‌نویس سند — بدون تغییر کد/PR/deploy
**مرجع:** `prompt-redesign-v1.md` (همین پوشه)، ریپو `rashidhamedas-prog/Site-B2B`، فایل پنل: `apps/web/src/components/admin/AdminOmnichannel.tsx`

## ۱. هدف راهبردی (یک جمله)
پنل «کانال انتشار» باید **تنها نقطهٔ کنترل** انتشار در تلگرام، روبیکا و بله باشد: قابل‌ردیابی، قابل‌توقف، بدون خودکاری ناخواسته، و با تأیید صریح مالک برای هر ارسال زنده.

## ۲. قوانین حاکمیتی (غیرقابل مذاکره — شرط ورود به هر فاز)
| # | قانون | پیاده‌سازی لازم در پنل |
|---|---|---|
| G1 | انتشار تلگرام **فقط از پنل سایت** (از مسیر Worker) | هیچ مسیر جانبی؛ اسکریپت/Bot API مستقیم ممنوع |
| G2 | انتشار زنده روبیکا و بله **در وضعیت HOLD** تا اعلام حامد | کلید HOLD/Kill-switch برای هر کانال؛ **پیش‌فرض: خاموش (ارسال زنده غیرفعال)**؛ فقط canary بله (4858359991) مجاز برای تست |
| G3 | ارسال زنده = **تأیید صریح مالک** | دکمهٔ «ارسال زنده» فقط پس از تأیید owner (حامد) با ثبت نام، زمان و فهرست اقلام |
| G4 | **بدون انتشار خودکار** | هیچ cron/trigger که بدون تأیید ارسال کند؛ زمان‌بندی فقط برای آیتم‌های از پیش تأییدشده |
| G5 | **لاگ ممیزی** کامل | چه کسی، چه چیزی، کجا، کی ارسال/ویرایش/حذف کرد؛ غیرقابل ویرایش |
| G6 | **حذف با تأیید** | دیالوگ تأیید دومرحله‌ای + پشتیبان محتوا قبل از حذف |
| G7 | **dedupe پیش از ارسال** | کلید یکتای «محصول + کانال (+ نسخهٔ محتوا)»؛ ارسال تکراری بلاک می‌شود |
| G8 | اقدام مستقیم سمت ربات **قابل‌مشاهده و ممنوع** | تطبیق دوره‌ای پست‌های کانال با رکوردهای پنل؛ هر پست/حذف بدون رکورد پنل = «اقدام خارج از پنل» با هشدار قرمز |

> **زمینهٔ حادثه:** اخیراً یک agent مستقیماً از طریق ربات ۵ محصول در بله منتشر و ۱۱ پست تکراری را حذف کرد، بدون تأیید قطعی. G5، G7 و G8 دقیقاً برای جلوگیری و قابل‌ردیابی‌کردن این نوع رخداد است. این رخداد باید به‌عنوان اولین رکورد دستی در لاگ ممیزی ثبت شود.

## ۳. اولویت‌ها
### P0 — ضروری (بدون این‌ها هیچ ارسال زنده‌ای مجاز نیست)
1. Kill-switch/HOLD هر کانال با نمایش وضعیت واقعی provider (جایگزین `OMNICHANNEL_DISABLED_PROVIDERS` بی‌صدا) + هشدار هنگام تغییر.
2. جریان تأیید owner برای ارسال زنده؛ حذف auto-publish.
3. لاگ ممیزی (ارسال/ویرایش/حذف/تغییر کلید/تأیید) + تشخیص اقدامات خارج از پنل.
4. Dedupe قبل از ارسال (idempotency key) و صف مقاوم به restart/deploy.
5. وضعیت هر delivery: `queued` / `succeeded` / `failed` / `dead` + **حالت جدا «هشدار» (کهربایی)** برای succeeded همراه با warning. امروز در `AdminOmnichannel.tsx` (حدود خط ۲۰۲۲) هشدارِ deliveryهای موفق قرمز و مثل خطا نمایش داده می‌شود → گمراه‌کننده.
6. Retry فقط برای `failed`؛ برای `dead` فقط retry دستی با تأیید و پس از رفع علت. `unsupported_media` (طبق PR #109) **غیرقابل‌retry** و مستقیم DEAD — دکمهٔ retry برای آن غیرفعال با توضیح «اول تصویر را اصلاح کنید».
7. Dry-run: شبیه‌سازی کامل (کپشن، رسانه، dedupe، کانال مقصد) بدون ارسال.
8. حذف از پنل با تأیید و پشتیبان.

### P1 — مهم
1. سلامت/ممیزی تصویر: اعتبارسنجی هنگام آپلود، تولید JPEG امن‌کانال **<1.8MB** برای بله/روبیکا (PR #109)، فهرست محصولات با تصویر خراب (نمونه: محصول **5047** نیازمند آپلود مجدد).
2. پیش‌نمایش هر کانال (کپشن + تصویر نهایی بعد از فشرده‌سازی).
3. زمان‌بندی (فقط آیتم‌های تأییدشده) + ساعت سکوت ۲۳–۱۲ + سقف روزانه.
4. ماتریس پوشش محصول × کانال (اختلاف روبیکا ۳۰ / بله ۲۴ طبق brief) با «دلیل ثبت‌شده» برای هر عدم‌پوشش.
5. منبع واحد حداقل سفارش، قیمت، آیدی تماس و لینک محصول در کپشن.
6. داشبورد سلامت مسیر Worker تلگرام (دامنه اختصاصی).

### P2 — بعداً
1. صندوق پیام و پیش‌فاکتور ربات‌ها (پس از تثبیت انتشار).
2. قالب کپشن پیشرفته/A-B، گزارش روند.
3. نقش‌های دسترسی ریزدانه‌تر (ویراستار/تأییدکننده/مشاهده‌گر).

## ۴. KPIها (تعریف + روش اندازه‌گیری از دادهٔ موجود)
> هیچ عدد پایه‌ای در این سند ادعا نمی‌شود. **اهداف ستون آخر «پیشنهاد» هستند** و باید پس از اندازه‌گیری پایه توسط حامد تأیید شوند.

| KPI | تعریف | منبع/روش اندازه‌گیری | هدف پیشنهادی |
|---|---|---|---|
| سهم انتشار از پنل | تعداد پست‌های کانال دارای رکورد پنل ÷ کل پست‌های کانال | تطبیق جدول deliveryها با پیام‌های کانال (getUpdates/تاریخچه) | پیشنهاد: ۱۰۰٪ |
| نرخ موفقیت تحویل | succeeded ÷ (succeeded+failed+dead) به تفکیک کانال | جدول delivery/وضعیت‌ها | پیشنهاد: ≥۹۹٪ (از brief) |
| نرخ هشدار | succeeded-with-warning ÷ succeeded | فیلد warning در delivery | پیشنهاد: روند نزولی |
| DEAD به تفکیک علت | تعداد dead per error code (مثلاً unsupported_media) | کد خطای delivery | پیشنهاد: صفر DEAD بدون اقدام بیش از ۲۴ ساعت |
| پست تکراری | تعداد جفت «محصول+کانال» با بیش از یک پست فعال | گروه‌بندی deliveryهای succeeded | پیشنهاد: صفر |
| اقدام خارج از پنل | پست/حذف در کانال بدون رکورد پنل | گزارش تطبیق G8 | پیشنهاد: صفر |
| اختلاف پوشش بی‌دلیل | محصولات منتشرشده در یک کانال و نه دیگری بدون دلیل ثبت‌شده | ماتریس پوشش | پیشنهاد: صفر |
| سلامت تصویر | محصولات با تصویر نامعتبر/بالای حد ÷ کل محصولات فعال | اسکن رسانه | پیشنهاد: صفر برای محصولات در صف |
| ارسال زندهٔ بدون تأیید | ارسال زنده بدون رکورد تأیید owner | لاگ ممیزی | **الزام: صفر** (قانون، نه هدف) |

## ۵. موارد جاافتاده در brief
1. **وضعیت HOLD روبیکا/بله** و کلید پیش‌فرض خاموش اصلاً ذکر نشده.
2. **جریان تأیید owner** برای ارسال زنده (brief فقط «GO نوشتاری» برای deploy دارد، نه برای هر ارسال).
3. **تشخیص اقدامات مستقیم ربات** و تطبیق کانال با پنل.
4. **حالت «هشدار» جدا از خطا** و قواعد retry به تفکیک وضعیت/کد خطا (PR #109).
5. **Dry-run** نیامده.
6. سیاست نگهداری لاگ ممیزی و پشتیبان پست‌های حذف‌شده (مدت، محل).
7. نقش‌ها و دسترسی‌ها در پنل (چه کسی می‌تواند تأیید/حذف کند).
8. KPIها بدون تعریف و روش اندازه‌گیری و بدون خط پایه.
9. برنامهٔ پاک‌سازی/ثبت رخداد بله اخیر (۵ انتشار، ۱۱ حذف).
10. رفتار هنگام برداشتن HOLD (آیا صف عقب‌افتاده خودکار می‌رود؟ → **نه؛ باید دوباره تأیید شود**).

## ۶. ریسک‌ها
| ریسک | اثر | کاهش |
|---|---|---|
| دور زدن پنل با ربات/اسکریپت | تکرار حادثهٔ بله، از دست رفتن اعتماد | G8 + محدودسازی دسترسی توکن روی سرور |
| برداشتن HOLD و تخلیهٔ ناگهانی صف | انتشار انبوه ناخواسته | صف پس از HOLD «معلق» می‌ماند تا تأیید مجدد |
| هشدار قرمز = خطا | retry اشتباه و پست تکراری | حالت کهربایی + retry فقط failed/dead |
| retry روی unsupported_media | حلقهٔ شکست | DEAD غیرقابل‌retry تا اصلاح تصویر |
| deploy وسط ارسال | پست ناقص/تکراری | idempotency + صف پایدار |
| تصویر خراب (مثل 5047) | DEAD یا پست بی‌کیفیت | اعتبارسنجی هنگام آپلود + گزارش سلامت |
| ادعای تأییدنشده (ضدآب) و قیمت نادرست | ریسک حقوقی/اعتبار | فقط از منبع تأییدشده، پیش‌نمایش |
| نشت توکن در UI/لاگ | امنیتی | ماسک کامل، بازبینی امنیت |

## ۷. معیارهای پذیرش (Acceptance Criteria)
- [ ] هر کانال کلید HOLD مستقل دارد؛ پیش‌فرض روبیکا و بله = HOLD؛ تغییر آن فقط با نقش owner و ثبت در لاگ.
- [ ] با HOLD فعال، هیچ ارسالی به کانال اصلی انجام نمی‌شود (تست: تلاش ارسال → بلاک با پیام روشن).
- [ ] ارسال زنده بدون رکورد تأیید owner ممکن نیست (تست منفی).
- [ ] هیچ مسیر auto-publish در کد/cron وجود ندارد (بازبینی کد).
- [ ] ارسال دوبارهٔ «محصول+کانال» فعال بلاک یا به «ویرایش» هدایت می‌شود.
- [ ] هر ارسال/ویرایش/حذف/تغییر کلید/تأیید با کاربر، زمان، کانال، شناسهٔ پیام در لاگ ممیزی است و قابل‌ویرایش نیست.
- [ ] پست‌های کانال بدون رکورد پنل در گزارش «اقدام خارج از پنل» ظاهر می‌شوند.
- [ ] حذف نیازمند دیالوگ تأیید + پشتیبان است.
- [ ] وضعیت‌ها: queued/succeeded/failed/dead + «هشدار» کهربایی برای succeeded با warning (رفع رنگ قرمز در `AdminOmnichannel.tsx` ~L2022).
- [ ] retry فقط برای failed/dead؛ unsupported_media غیرقابل‌retry با راهنمای اصلاح تصویر.
- [ ] تصاویر بله/روبیکا JPEG زیر 1.8MB؛ آپلود فایل خراب رد می‌شود؛ گزارش سلامت تصویر محصول 5047 را نشان می‌دهد تا اصلاح شود.
- [ ] پیش‌نمایش جدا برای هر کانال و dry-run بدون هیچ فراخوانی Bot API واقعی.
- [ ] زمان‌بندی فقط برای آیتم تأییدشده؛ ساعت سکوت و سقف روزانه اعمال می‌شود.
- [ ] تست ابتدا روی canary بله؛ هر فاز با PR کوچک، ریسک، راه برگشت و GO نوشتاری حامد.

## ۸. تصمیم‌های مورد نیاز از حامد
1. تأیید فهرست P0 به‌عنوان شرط برداشتن HOLD.
2. تعیین نقش owner/تأییدکننده (فقط حامد یا نماینده؟).
3. تأیید اهداف پیشنهادی KPI پس از اندازه‌گیری پایه.
4. مدت نگهداری لاگ ممیزی و پشتیبان حذف.
