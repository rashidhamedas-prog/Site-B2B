## تصمیم‌های قطعی حامد (تغییر نده)
1. همه اتصال‌ها LIVE می‌مانند. HOLD پیش‌فرض و تأیید Owner برای هر ارسال لازم نیست. فقط دکمهٔ «توقف اضطراری» دستی Owner اضافه شود.
2. هر کانال (تلگرام، روبیکا، بله) متن، قالب کپشن، جزئیات، آیدی تماس، UTM، سقف روزانه، فاصلهٔ پست‌ها، ساعت سکوت و owner_chat_id **کاملاً جدا** دارد. هیچ تنظیم مشترک سراسری برای محتوا نباشد. مقدار آیدی‌ها را حامد خودش از پنل وارد می‌کند. مقدار پیش‌فرض نگذار.
3. حداقل سفارش از فیلد تعریف‌شده روی هر محصول خوانده شود. اگر مقدار نداشت، در کپشن نیاید و هشدار نشان داده شود.
4. ربات تلگرام عمده همان @TaranomRetailBot می‌ماند.
5. واژهٔ «ضدآب» در کپشن‌ها مسدود شود.
6. مقصد فوروارد پیام ربات‌ها یک فیلد قابل‌ویرایش در پنل باشد، جدا برای هر کانال.
7. سقف، فاصله و ساعت سکوت برای هر کانال قابل شخصی‌سازی کامل باشد.
8. ربات‌های سفارش‌گیر آخرین فاز هستند، بعد از تثبیت انتشار.

## اولین PR: رفع نقص drain
بعد از تست drain، با حذف فایل `/tmp/omnichannel-worker.drain` حالت stopping در حافظهٔ worker پاک نمی‌شود و worker تا restart متوقف می‌ماند. اصلاح لازم:
- اگر فایل drain حذف شد و drain هنوز کامل نشده یا فایل drained پاک شده، worker به حالت عادی برگردد و دوباره claim کند.
- برای سناریوهای drain، cancel و resume تست بنویس.

## قوانین سخت (در همه PRها)
- انتشار، ویرایش و حذف فقط از طریق پنل. اسکریپت یا Bot API مستقیم برای عملیات کاربر ممنوع است.
- تلگرام فقط از مسیر TELEGRAM_API_URL. این مسیر را عوض نکن.
- توکن هرگز در کد، لاگ، UI، تست یا خروجی نیاید، حتی ماسک‌شده.
- کلید صف idempotent باشد (بدون Date.now())، claim اتمی باشد، revive خودکار نداشته باشد، و ارسال نامشخص به HOLD برود.
- برای حذف و ویرایش پست: قبل از حذف پشتیبان گرفته شود، تأیید دومرحله‌ای داشته باشد و در لاگ ممیزی ثبت شود.
- انتشار گروهی پیش‌فرض خاموش باشد. پست‌های DEAD قدیمی retry نشوند.
- migrationهای DB فقط افزایشی و برگشت‌پذیر باشند، بدون حذف داده. قبل از هر migration از DB پشتیبان گرفته شود.
- قیمت، موجودی و ادعای محصول فقط از دیتابیس خوانده شوند.

## روال هر PR
1. branch بساز، پیاده‌سازی کن و تست واحد، یکپارچه و UI بنویس.
2. CI کامل باید سبز باشد: lint-and-build، omnichannel-migrate، CodeQL و تست‌ها. اگر چیزی قرمز شد، اصلاح کن. تست را skip یا حذف نکن.
3. squash-merge به master.
4. deploy فقط با `scripts/auto-deploy.sh` و فایل approval معتبر برای همان commit، با مرجع «GO حامد ۲۷ اکتبر، بستهٔ بازطراحی». FORCE و SKIP_DRAIN ممنوع است.
5. قبل از deploy:
   - صف خالی باشد (PENDING، PROCESSING، RETRY، SENDING و lockedAt همه صفر).
   - خارج از ساعت سکوت هیچ ارسالی در جریان نباشد.
   - deploy در حین انتشار ممنوع است.
6. بعد از deploy (smoke test):
   - health api
   - worker سالم باشد و heartbeat داشته باشد
   - صف سالم باشد
   - صفحهٔ پنل باز شود
   - تست drain و برگشت به کار
   - **در کانال‌های واقعی چیزی منتشر نکن.** تست انتشار فقط روی canary بله (4858359991) و حداکثر یک پست.
7. اگر smoke شکست خورد، فوراً rollback کن (revert همان PR و deploy، یا image قبلی) و کار را متوقف کن.

## شرایط توقف (فوراً متوقف شو و گزارش بده)
- CI بعد از ۳ بار تلاش برای اصلاح هنوز قرمز است.
- smoke بعد از deploy شکست خورد یا rollback لازم شد.
- کاری لازم شد که خارج از این بسته است، مثل تلگرام egress، تغییر env حساس، حذف داده یا انتشار واقعی.
- تصمیمی لازم شد که در تصمیم‌های قطعی بالا نیست. به‌جای حدس، توقف کن.

## گزارش نهایی
- فهرست PRها با لینک، commit، نتیجهٔ CI و وضعیت deploy
- نیازهای پوشش‌داده‌شده و باقی‌مانده با شناسه REQ
- هر rollback یا توقف با علتش
- commit و image در حال اجرا روی سرور
- آماده‌بودن برای فاز تلگرام
